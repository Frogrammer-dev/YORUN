# 이미지 인식으로 알아볼 만한 러닝 코스를 발견한다

현재 개선이 멈춘 이유는 단순히 인식 모델이 작아서가 아니다. **실제 도로 후보를 만드는 능력, 그 선을 알아보는 능력, 이름을 붙여 추천해도 되는지 판단하는 능력이 하나의 분류 점수로 묶여 있다.** AI 인식·후보 생성 전문가, 모델 조사 전문가, 평가 전문가의 검토를 합치면, 먼저 같은 후보에서 입력 표현과 인식 방법을 비교하고, 후보 풀 안에 사람에게 알아볼 만한 그림이 있는지 따로 확인해야 한다. 제품의 핵심은 여전히 “도로에서 무엇처럼 보이는 경로를 발견한다”이며, 템플릿 전용 추천으로 바꿀 이유는 없다. 권장 실험 구조는 저렴한 기하·동결 임베딩으로 후보를 추리고 서버 VLM으로 이름 제안과 거절을 수행한 뒤, 사람 평가로 표시 기준을 보정하는 방식이다. 다만 이 구조가 현재 모델보다 낫다는 결과는 아직 없으므로, 고정 후보 비교를 통과해야 운영에 넣는다. 서버 AI는 허용하되 소수의 정규화 선화만 전송하며, 비용과 지연을 품질과 함께 측정한다. 이번 작업은 코드와 기존 평가 자료를 분석하고 연구를 수집한 것이며, 앱 수정·새 모델 추론·사람 평가는 수행하지 않았다.

## 높은 낙서 점수가 사람이 보는 닮음을 보장하지 않는다

현재 흐름은 도로 그래프에서 코스 후보를 만들고, `recognizeCourses`가 이름과 점수를 붙인 다음 `pickDoodles`와 `nameDiscoveries`가 화면에 표시할 코스를 고르는 구조다. 인식기는 경로를 28×28 단색 이미지로 만들고 −12도·0도·12도 결과를 평균 낸다. 단순 도형 등을 제외한 클래스 중 최고 점수를 선택하기 때문에, 허용 클래스에 양의 점수가 있으면 “아무 사물도 안 보임” 대신 이름을 붙인다. 클래스 제외 뒤 확률을 재정규화하는 구조는 아니지만, 제외된 단순 도형이 더 적합할 때 사물 이름을 거절하는 정책도 없다. 표시 기준은 현재 35점이며, 보정 파일은 `calibrated=false`, `labels=0`이다. **이 점수는 사람이 해당 이름을 납득할 확률이 아니다.** ([인식 코드](<C:/Users/ekdus/OneDrive/바탕 화면/running/src/lib/art/recognize.ts>), [표시 코드](<C:/Users/ekdus/OneDrive/바탕 화면/running/src/lib/route/present.ts>), [보정 설정](<C:/Users/ekdus/OneDrive/바탕 화면/running/src/lib/eval/calibration.json>))

기존 블라인드 평가에서 방식별 20개에 대한 두 VLM 판정 평균은 낙서 인식 0%, 동네 고리 35%, 그림 지정 15%였다. 양 94점·고슴도치 90점처럼 높은 점수의 추천도 두 판정자가 알아보지 못한 사례가 있다. 이는 현재 표시 이름에 문제가 있다는 강한 신호지만, **사람 인식률 0%나 모든 후보의 실패를 뜻하지 않는다.** 강남 두 영역과 두 거리 조건의 상위 결과이며, 방식별 탐색 예산도 다르다. 기본 도형을 제외한 동네 고리의 분모는 5개뿐이다. 두 VLM을 최종 사람 정답으로 삼거나 이 수치만으로 모델 우열을 결정해서는 안 된다. 입력 분포 차이는 확인됐다. ## 같은 후보를 비교해야 모델 교체의 효과를 판단할 수 있다

첫 실험은 **현재 DoodleNet을 그대로 두고 이진 입력과 회색 경계 입력을 비교하는 것**이다. 저장한 동일 후보 200~500개에 선 두께·여백·축소 방식을 한 변수씩 바꾼다. 28×28 입력에는 초고해상도에서 그린 뒤 축소한 회색 선화를 포함하고, 후속 모델용으로 종횡비를 유지한 224/256 이미지도 만든다. 사람이 만든 알아볼 만한 한 획 윤곽과 실제 GPS 아트 양성, 의미 없는 폐곡선 음성을 함께 둔다. 양성에서도 실패하면 입력·인식 문제가 크고, 양성은 잘 읽지만 실제 후보에 좋은 그림이 없으면 생성 문제가 크다. 렌더링·모델·후보를 동시에 바꾸면 원인을 분리할 수 없다.

이후 같은 후보에 현재 CNN, 동결 CLIP/SigLIP의 이미지-텍스트 검색, 단선 윤곽 예시를 이용한 이미지-이미지 검색, 서버 VLM을 비교한다. CLIP은 이미지와 문장을 비교할 수 있지만 공식 카드가 도메인 검증과 후보 클래스 구성에 따른 성능 변화를 명시한다. SigLIP 2도 검색과 임베딩을 지원한다. 이들은 의미 사전을 넓히는 후보이며 도로 선화에서 더 낫다는 보장은 없다. 스케치 검색 연구는 표현과 구조를 별도로 다루지만 사진 검색의 성능을 이 제품의 이름 추천 성능으로 옮길 수 없다. **CLIP/SigLIP 교체는 실험 가설이지 해결 완료가 아니다.** ([CLIP 모델 카드](https://github.com/openai/CLIP/blob/main/model-card.md), [SigLIP 2 공식 카드](https://huggingface.co/google/siglip2-base-patch16-224/blob/main/README.md), [Sketch_LVM 원 논문](https://openaccess.thecvf.com/content/CVPR2023/papers/Sain_CLIP_for_All_Things_Zero-Shot_Sketch-Based_Image_Retrieval_Fine-Grained_or_CVPR_2023_paper.pdf), [Sketchy 원 연구](https://patsorn.me/projects/sketchy/))

권장하는 검증 대상 구조는 로컬 또는 자체 서버의 저렴한 임베딩으로 전체 후보를 평가하고, 형태가 다양한 상위 8/16/32개만 외부 VLM에 보내는 방식이다. 브라우저 실행이 검증되기 전에는 오프라인·자체 서버에서 동결 모델을 비교해도 된다. VLM은 먼저 예상 이름 없이 자유 명명 또는 `none`을 답하고, 다음 검증 단계에서 제안 이름의 수용 여부를 평가한다. 결과에는 `label`, `visibleFeatures`, `missingFeatures`, `orientation`, `rejectReason`을 남긴다. 존재하지 않는 눈·다리를 근거로 설명하면 탈락시킨다. 생성자의 확신이나 설명을 검증자에게 그대로 주지 않는다. 다만 같은 모델 계열의 합의도 독립 사람 판단을 대체하지 못하고, VLM 자기 확신 역시 품질 확률로 표시하지 않는다.

이 구조의 핵심 조건은 앞단이 좋은 후보를 버리지 않는 것이다. 원래 풀에서 사람이 알아본 후보를 shortlist가 얼마나 보존하는지 먼저 측정한다. VLM이 사람 평가에서 품질 증가를 보이지 않으면 운영 호출을 넣지 않는다. 동결 임베딩이 개선하지 못하면 스케치 예시 검색이나 현재 CNN의 보정이 더 적합할 수 있다. 운영 모델을 정한 뒤에만 실제 경로의 긍정·부정쌍과 사람의 쌍별 선호로 작은 순위 모델 또는 adapter를 학습한다. 사람 동의 없는 VLM 의사 라벨은 학습 정답으로 취급하지 않는다.

## 좋은 그림이 후보에 없는지 먼저 확인한다

현재 고리 생성은 블록 합집합의 단순 폐곡선을 유지하며 구멍과 점 접촉을 막는다. 확장 중 의미 인식 점수를 쓰지 않고, 인식 풀은 길이 범위 안 고리의 일정 간격 표본 등을 이용한다. 왕복 가지 실험은 표현 가능한 모양을 넓히지만, 이름 종류나 최고 확신 증가가 사람에게 더 닮아 보인다는 검증은 아니다. 장소의 bounding box가 많이 겹치면 제거하는 중복 기준도 형태가 다른 코스를 지울 수 있다. ([고리 생성](<C:/Users/ekdus/OneDrive/바탕 화면/running/src/lib/route/loops.ts>), [후보 풀](<C:/Users/ekdus/OneDrive/바탕 화면/running/src/lib/route/discover.ts>), [가지 생성](<C:/Users/ekdus/OneDrive/바탕 화면/running/src/lib/route/branches.ts>))

따라서 사람에게 이름을 숨긴 후보 풀을 보여 주고, 해당 지역·거리 조건에서 알아볼 만한 후보가 최소 하나 있는지 확인하는 **후보 oracle 조사**가 필요하다. 여기서 oracle은 사람이 확인한 후보 가능성이며 AI 점수 최고값이 아니다. 후보 안에 좋은 그림이 있는데 상위 추천에서 놓치면 인식·순위 문제다. 풀 전체에도 없다면 모델보다 탐색을 개선해야 한다. 전수 판정이 부담스러우면 방법·점수별 층화 표본과 각 모델 top-k 합집합을 먼저 판정하되, 이를 전체 풀의 상한이 아닌 표본 oracle로 보고한다. 낮은 결과를 보인 대표 조건만 전체 후보를 검토한다.

생성 병목이 확인되면 동일 시간·단계 예산 아래 고리 300, 고리 1000, 고리와 가지, 형태 다양성을 고려한 300 후보를 비교한다. 다음 단계에서 그림 유도 탐색과 자유 그래프 walk를 추가한다. 단순 폐곡선, 돌출 가지, 내부 선, 반복 구간 등 위상과 형태별로 후보를 보존하고, 장소 중복과 모양 중복을 분리한다. 가지 길이·왕복 비율·회전 수·총거리·도로 연결성을 함께 기록해야 그림 품질과 달리기 부담을 바꾸어 얻은 효과를 구별할 수 있다. 템플릿은 이 후보 공급원 중 하나로 남긴다. 이미지 인식이 여러 공급원에서 사물처럼 보이는 경로를 발견하는 제품 방향은 유지한다.

모델 점수로 후보 생성을 직접 최적화하는 것은 후순위다. 높은 점수의 오인이 이미 존재하므로 점수만 올리면 사람이 더 알아보기 어려운 모양을 만들 위험이 있다. 먼저 다양성·거리·반복거리 제약과 인간 평가 기준을 세운 뒤, 생성 중 의미 점수를 쓰는 효과를 별도 검증한다. 실제 OSM 연결성은 현장의 횡단 안전성과 현재 접근 가능성을 보장하지 않으므로, 의미 평가를 통과한 경로도 기존 도로·안전 검증을 거쳐야 한다.

## 사람 평가를 통과할 때만 이름을 표시한다

파일럿은 격자 도심·비정형 구도심·해안·공원 등 비중첩 12개 지역과 2개 거리 조건, 총 24개 요청 조건으로 제안한다. 지역 6개는 개발, 3개는 표시 기준 보정, 3개는 최종 보류 시험에 둔다. 같은 경로의 회전·번역본과 겹치는 지도는 분할을 넘지 않는다. 후보당 최소 3명이 방법·점수·이름을 숨긴 상태에서 자유 이름 또는 “아무것도 안 보임”을 답하고, 답을 잠근 뒤 제안 이름의 납득도를 평가한다. 마지막에 달리고 싶은지를 묻는다. 이름 공개 전 인식과 공개 후 납득은 서로 다른 지표다. 뜻이 같은 이름과 복수 해석을 저장하고, 애매한 답은 독립 검토한다.

핵심 지표는 의미 있는 사물 이름의 수용 정밀도, 음성 후보 오인율, 전체 지역·거리 중 유용한 추천이 하나 이상 나오는 비율이다. 여기에 풀의 후보 가능성, fixed-pool recall@k, 이름 다양성, 지연 p50/p95, 메모리와 비용을 붙인다. 단순 도형은 별도 집계한다. 추천을 전부 거절하면 정밀도만 좋아 보이므로 추천이 나오는 조건 비율을 반드시 함께 본다. 예측 거절은 오류와 coverage를 교환하는 접근이며, 보정된 확률도 분포가 바뀌면 재검증이 필요하다. ([Selective classification 원 논문](https://arxiv.org/abs/1705.08500), [확률 보정 연구](https://proceedings.mlr.press/v70/guo17a.html), [분포 변화의 불확실성 연구](https://arxiv.org/abs/1906.02530))

**제안 성공 기준이며 아직 달성 결과가 아닌 목표**는 의미 이름 수용 정밀도 80% 이상과 Wilson 95% 하한 70% 이상, 음성 오인율 10% 이하, 기존 방식보다 높은 유용 추천 조건 비율이다. 서로 겹치는 코스나 한 코스의 세 사람 판정을 독립 경로처럼 세지 않고 지역·조건 단위 불확실성도 보고한다. 24조건 파일럿은 방향 결정용이며 출시 성능 확정에는 추가 보류 지역이 필요하다. 기준을 만족하는 임계값이 없으면 의미 이름 추천을 `unavailable`로 처리한다. “이 범위에서 알아볼 만한 그림 코스를 찾지 못했습니다”와 거리·범위 변경을 제시하면 억지 이름을 줄일 수 있다.

구현 순서는 평가 스키마·빈 보정 방어와 후보 재현 로그 정비 0.5~1일, 같은 모델의 렌더링 비교 1~2일, 고정 후보 모델 비교 2~4일을 우선 제안한다. 생성 실험 2~5일은 oracle 결과가 그 병목을 가리킬 때 진행한다. 숙련 엔지니어 한 명의 계획 추정이며 사람 모집·라벨링과 학습 기간은 별도다. `src/lib/art/doodle.ts`에 재현 가능한 렌더 설정을, `recognize.ts`에 top-k·원점수·거절 사유·방향·모델 버전을, `present.ts`에 보정된 표시·거절 정책을 넣는 경계가 적절하다. `finder.worker.ts`, `discover.ts`, `branches.ts`는 후보 출처와 다양성 실험을 담당하고 `RouteFinderApp.tsx`는 검증된 결과를 연결한다. 원래 `prob`는 사람 인식 확률과 분리해 보관한다. 이 순서는 모델 성능과 도로 생성의 효과를 섞지 않고 기존 구조를 활용한다.

## 서버 AI 비용은 후보 수와 개인정보 최소화로 관리한다

모든 후보를 외부 VLM에 보내는 구조보다 shortlist를 우선 검증한다. 24조건에서 후보 300개씩 전송하면 7,200이미지이며, 16개씩이면 384이미지로 **이미지 검증 수가 18.75배 차이** 난다. 이는 호출 수 비교이지 토큰 비용이나 품질이 같은 비율로 바뀐다는 뜻은 아니다. 실제 요청당 비용은 `shortlist 수 × 캐시 미스율 × 후보당 호출 수 × 실측 평균 호출비`이고 총비용은 입력·출력·thinking 토큰 단가, 자체 서버비, 재시도로 산정한다. 여러 후보를 한 판에 넣을 경우 ID 혼동·위치 편향·형태 축소도 검증해야 한다.

2026년 10월 10일 조사한 Gemini 공식 가격표의 예로, 2.5 Flash standard는 입력 백만 토큰당 $0.30, 출력은 thinking 포함 $2.50이며 Flash-Lite는 $0.10/$0.40이다. Flash의 입력 10,000토큰·출력 및 thinking 1,000토큰이라는 **가정**에서는 요청당 $0.0055, 1만 요청 $55다. 이는 경로 몇 개가 해당 토큰을 사용한다는 실측이 아니다. 실험에서 usage와 재시도를 기록하고 운영 시점 가격을 다시 확인해야 한다. 모델 선택은 이 예시 단가가 아니라 사람 품질 증가량 대비 비용과 지연으로 결정한다. ([Gemini 공식 가격표](https://ai.google.dev/gemini-api/docs/pricing))

로컬 모델은 외부 호출비와 정보 전송을 줄이지만 다운로드·초기 로딩·배터리·모바일 메모리 부담이 있다. Transformers.js는 WebGPU 실행을 지원하지만 특정 SigLIP checkpoint의 변환과 모바일 성능까지 보장하지 않는다. 자체 서버 임베딩은 재현성과 모델 관리가 편하지만 CPU/GPU 비용과 동시 처리량을 측정해야 한다. 초기 비교는 오프라인·자체 서버, 운영 후보는 품질이 검증된 뒤 브라우저 가능성까지 평가하는 순서가 합리적이다. ([Transformers.js WebGPU 문서](https://huggingface.co/docs/transformers.js/en/guides/webgpu))

외부 API 기본 입력은 원점과 절대 크기를 제거한 선화와 불투명 candidate ID로 제한한다. 지도 타일·출발점·주소·좌표·사용자 식별자·개인 러닝 기록은 보내지 않는다. **정규화 선화도 공개 지도와 대조하면 지역이 추정될 수 있어 완전 익명화라고 표현할 수 없다.** 외부 업체의 보관·사용 조건도 비교해야 한다. Gemini 약관상 무료 서비스는 입력과 응답을 제품 개선에 사용하고 사람이 검토할 수 있으며, 유료 서비스는 개선에 사용하지 않지만 악용 탐지 로그와 일시적 국외 저장 관련 조건이 있다. “학습에 사용하지 않음”을 “저장하지 않음”으로 설명하면 안 된다. 운영 키는 서버에서 관리하고, geometry fingerprint·렌더·모델·프롬프트 버전으로 캐시를 구성하며, 실패 시 보정된 로컬 결과 또는 `none`을 반환한다. 이번 조사에서 외부 모델에 프로젝트 경로를 업로드하지 않았다. ([Gemini 공식 약관](https://ai.google.dev/gemini-api/terms))

개선의 첫 판단점은 더 큰 AI를 골랐는지가 아니라, 같은 후보에서 사람이 알아볼 만한 경로를 더 잘 찾아냈는지다. 고정 풀 비교가 인식 병목을, 후보 oracle이 생성 병목을 드러내면 다음 개발 투자를 근거 있게 선택할 수 있다. 그 뒤에야 실제 경로 데이터로 학습을 시작한다. 이 방식은 핵심 기능을 유지하면서 실패 원인을 측정 가능한 단위로 바꾸고, 좋은 모양이 없는 조건에서도 신뢰할 수 있는 추천 경험을 만든다.
