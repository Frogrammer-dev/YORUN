# 요런 아이디어 경진대회 중간발표 평가·구성안

평가일: 2026-10-22. 발표: 2026-10-26 월요일, 10분. 대회 심사표와 질의응답 시간 포함 여부는 미확인이다. 제품·기술 근거·시연 준비를 세 에이전트가 독립 검토한 뒤 현재 코드 확인 결과를 합쳤다.

## 판단

**중간발표에 적합하다. 핵심 웹 흐름을 구현하고, 경로 품질을 실험했으며, 모바일 기록 시제품까지 확장한 단계다. 다음 과제는 기능 추가보다 사용자·실기기 검증이다.** 출시 가능한 통합 모바일 서비스나 수요가 검증된 사업으로 발표할 근거는 아직 부족하다. 평가표가 없어 예상 심사 점수나 수상 가능성은 판단하지 않는다.

발표 한 문장: “요런은 그림 러닝 코스를 직접 설계하는 부담을 줄이고, 주변 길에서 찾은 코스를 달려 나만의 작품으로 남기는 서비스입니다.”

초기 타깃은 ‘색다른 코스를 찾는 입문·취미 러너’라는 가설로 좁힌다. 운동 지속 효과와 재사용 의향은 검증할 질문이며 확정 성과가 아니다.

| 평가 축 | 현재 판단 | 발표에 필요한 보완 |
|---|---|---|
| 아이디어 전달 | 코스 찾기 → 기록 → 작품방으로 설명 가능 | 한 이용자와 한 상황으로 시작 |
| 구현 진척 | 중간발표에 충분한 시제품 | 실제 동작 영상과 구현 범위 표시 |
| 기술적 노력 | 실제 도로 제약·품질 개선 실험 근거 있음 | 성공·실패 사례를 같은 조건으로 비교 |
| 사용자 가치 | 가설 단계 | 5명 내외의 인터뷰·과업 관찰 |
| 모바일 실사용 | Android 시험 APK, 독립 기록 시제품 | 야외 잠금 기록과 복원 시험 |
| 사업성·차별성 | 이 검토로는 입증되지 않음 | 심사표에 사업성이 있으면 기존 해결 방법·고객·수익 가설 1장 |

| 항목 | 근거에 맞는 표현 | 한계 |
|---|---|---|

| AI 참고 그림 | 도로에 이름·참고 그림을 붙이는 실험 기능 | 실제 외부 API 품질·비용과 사람 인식 성과는 미확인 |

2026-10-22 이번 평가에서 직접 실행한 검사: `npm run typecheck` 통과. `tests/shape-strokes.test.ts`, `tests/stroke-routes.test.ts`, `tests/components/custom-shape-input.test.tsx`, `tests/components/finder.test.tsx`, `tests/run.test.ts` 총 5파일 55테스트 통과. 전체 회귀·빌드·브라우저 시험을 새로 완료했다는 뜻은 아니다.

홈 화면의 고양이 그림과 기본 작품방 예시는 데모 그래픽이다. 실제 생성 결과·사용자 기록으로 소개하지 않는다. README의 과거 1.4–4초·81–88점과 위 고정 12조건 수치는 조건이 다르므로 하나의 성능 그래프로 합치지 않는다.

## 월요일 전 보완 우선순위

1. **실제 한 번의 사용 증거.** Android 기기에서 코스 전달·기록·GPX·작품방까지 시험한다. 가능한 경우 화면 켬 5분, 잠금 15분, 다른 앱 사용 등 10분으로 30분 기록을 확인한다. 기기/OS, 이동 시간, GPS 최대 공백, 배터리 변화, 복원 결과를 남긴다. 이동 중 휴대폰 조작은 멈춰서 한다. 실패도 조건·증상·다음 조치와 함께 발표 자료가 된다.
2. **5명 내외 사용자 관찰.** 코스 선택과 작품 확인을 설명 없이 해 보게 하고 완료 인원/참여 인원, 막힌 지점, 실제 발언을 기록한다. 경로 6개 정도는 이름을 먼저 숨기고 무엇처럼 보이는지 질문한다. 이름 공개 후에는 달리고 싶은지와 이유를 묻는다. 지인 편의표본이라는 점을 밝히고 시장 수요·지속률로 일반화하지 않는다.
3. **60–90초 시연 영상.** 코스 선택 → 실제 또는 모의 GPS 기록 → 작품방 결과를 연결한다. 모의 입력이면 화면에 표시한다. 검색 대기를 편집했으면 시간 압축임을 밝힌다. 발표 현장에서는 녹화본을 기본으로 하고 정지 화면도 보관한다.

남은 기간의 기능 확장은 멈추고 시연을 막는 오류만 수정한다. 대결은 현재 로컬 시뮬레이션이므로 온라인 매칭 성과로 제시하지 않으며, 핵심 흐름 뒤의 향후 확장 또는 부록에 둔다. 새 AI 모델, 공공 API, 전면 UI 개편, 스토어 배포는 발표 전 필수 항목이 아니다.

## 10분 PPT — 10장

아래 시간에는 시연 영상을 포함하며 합계 10분이다. 질의응답까지 10분이라면 본문을 8분으로 줄인다. 실제 리허설에서는 9분 30초 내에 끝내 여유를 확보한다.

| 장 | 시간 | 슬라이드 제목 | 핵심 자료·발표 내용 |
|---|---:|---|---|
| 1 | 0:30 | 달린 길이 나의 작품이 된다 | 요런 한 문장 + 결과 작품 한 장. 예시인지 실제 기록인지 표기 |
| 2 | 1:00 | 그림 러닝을 시작할 때의 어려움 | 초기 타깃, 현재 코스 준비 방식, 인터뷰 발언. 미조사 내용은 문제 가설로 표기 |
| 3 | 0:45 | 코스 발견에서 작품 보관까지 | 코스 찾기 → GPS 기록 → 작품방, 화면 3장 |
| 4 | 1:30 | 현재 시제품은 이렇게 동작한다 | 60–90초 영상. 실제 도로·실제 기록·모의 입력 구분 |
| 5 | 1:15 | 구현 과정에서 만난 세 가지 문제 | 도로 연결, 그림 품질, 모바일 백그라운드 제한과 각각의 대응 |
| 6 | 1:15 | 경로 품질을 어떻게 개선했나 | 같은 평가 조건의 65.75 → 77.42점, 대표 성공·실패, 목표 80 미달. 오프라인 실험 표시 |
| 7 | 1:00 | 실제 사용 검증에서 확인한 것 | 실기기 시험과 소수 사용자 관찰. 결과 미확보 시 준비 상황·검증 계획으로 변경 |
| 8 | 1:00 | 어디까지 됐고 무엇이 남았나 | 웹 구현 / Android 빌드 / iOS·실기기 미검증 / 파일 연결 상태표 |
| 9 | 1:00 | 최종발표까지의 계획 | 현장 기록 안정성 → 흐름 통합 → 사용자 재시험. 각 단계 완료 기준과 담당자 |
| 10 | 0:45 | 다음에 증명할 가치 | “사용자가 스스로 코스를 고르고 작품까지 완성하는가?” 기대 가치와 검증 약속 |

기술 설명은 라이브러리 목록 대신 “왜 어려웠고, 무엇을 바꿨고, 결과가 어땠는가”로 말한다. 역할 분담은 실제 수행 내용으로만 적는다. 심사표가 사업성 중심이면 9장 일부를 초기 고객·기존 해결 방법·수익 가설로 바꾸되 경쟁 우위는 별도 조사 후 작성한다.

## 예상 질문과 답변 방향

- **기존 러닝 앱과 무엇이 다른가?** 주변 길에서 그림 코스를 찾고 실제 기록을 작품으로 모으는 경험을 제안한다. 최초·독점 기능이나 경쟁사 대비 우위는 조사 없이 주장하지 않는다.
- **정말 그림처럼 보이는가?** 기하학 점수와 사람이 알아보는 정도는 다르다. 대표 실패도 보여 주고 이름을 숨긴 사람 평가를 추가한다.
- **화면을 끄면 기록되는가?** 웹 제약을 확인해 네이티브 기록 시제품을 만들었다. 실기기 결과를 확보한 범위와 미완료 범위만 답한다.
- **안전하게 달릴 수 있는 길인가?** 지도 기반 보행 조건을 반영하지만 공사·통제·보도 등 실제 현장 상황을 보장하지 않는다.
- **사업성이 있는가?** 현재는 고객 문제와 핵심 경험을 검증하는 단계다. 결제 의향·재사용은 후속 검증으로 설명한다.
