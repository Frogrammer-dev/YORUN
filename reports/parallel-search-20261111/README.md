# 동네 추천 다듬기 병렬화 (2026-11-11)

## 무엇을 바꿨나
- 동네 추천은 '다듬기'(전체 시간의 70%)에서 상위 그림 3개를 차례로 다듬었다. 세 그림의 다듬기는 서로의 후보를 쓰지 않는다.
- `qualitySearch.ts`를 그림 하나 다듬기(`refineShape`)·합쳐 고르기(`finish`)로 나누고, 순차 `improveRoutes`는 같은 함수를 그대로 쓴다.
- 코어가 4개 이상이면 화면이 주 Worker + 보조 Worker 2개에 그림을 하나씩 보내고(그림마다 순차 때와 같은 남은 시간 몫), 주 Worker가 같은 규칙으로 합친다. 보조 Worker가 실패하면 그 그림은 주 Worker가 다듬는다. 코어 4개 미만·그림 지정·주변 비교·러닝 코스는 그대로 순차.
- 고정 12조건 벤치마크는 그림 지정 모드라 대상이 아니다.

## 사전 기준과 결과 (실제 도로, 단계 예산 20,000, 6지역 각 ±1000m, 3~8km)
- C1 리팩터 정확성: 원래 코드 사본과 새 순차 코드의 결과(코스 id·유사도)가 6지역 모두 **완전히 같음**. 비교 뒤 사본은 지웠다.
- C2 병렬 품질(1위 평균 하락 ≤ 1, 최악 ≤ 3, 상위3 평균 ≤ 1): **통과, 차이 0** (모든 지역 1위·상위3 같음). 결과: `steps20000.json`.
- 계산 시간(같은 기기, 다듬기만): 순차 대비 병렬 벽시계 40~53%.

## 브라우저 전체 시간 (로컬 개발 서버, 8코어, 이름 붙이기 끔)
| 지역 | 순차(코어 2개로 가장) | 병렬 | 결과 |
|---|---|---|---|
| 광안리 | 20.9초 | 13.2초 | 5개 이름·유사도 같음 |
| 둔산 | 24.4초 | 15.8초 | 6개 같음 |

## 한계
- 시간 예산에서는 보조 Worker가 코어를 실제로 받아야 같은 계산량이 된다. 코어가 적거나 발열로 느려지는 휴대폰에서는 이득이 줄고 결과가 순차와 달라질 수 있다.
- 실제 휴대폰·운영 배포에서는 아직 재지 않았다.
- 보조 Worker마다 길 그래프를 따로 들고 있어 메모리를 더 쓴다.
