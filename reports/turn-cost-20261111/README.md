# E4·H4b: 꺾임·지그재그 비용으로 잔물결 줄이기 (2026-11-11)

사전 등록: [protocol.md](protocol.md). 결과: `results.json`(E4), `h4b/results.json`(H4b). 기술 지표만 쟀고 사람·AI 인식 판정은 하지 않았다.

## 결론
- **E4(H4) 지지 안 함.** 윤곽 따라가기 생성기의 꺾임 비용을 5배·10배로 키워도 18조건 중 17조건에서 1위 경로가 같았다(같은 조건 J 비율 1.0). 이 생성기가 1위를 거의 만들지 않아 손잡이가 결과에 닿지 않았다.
- **H4b 지지 안 함.** 1위를 만드는 탐색 목적함수 4곳(블록 고리·배치 탐색·다듬기·배치 미세조정)의 지그재그 계수를 0.15·0.30으로 키우자 1위는 바뀌었지만 J 중앙값 비율 0.87·0.95로 T1(≤0.75) 실패. 줄어든 조건(광교 하트 0.019→0.008, 서면 고양이 0.048→0.001)과 늘어난 조건(둔산 고양이 0.003→0.034, 서면 하트 0.014→0.037)이 섞였다. 유사도 손실은 작았다(T2 통과).
- 기준 A는 E4와 H4b에서 완전히 같게 재현됐다(기본값 불변 확인).

## 비판과 다음 가설
- 탐색의 지그재그 항은 '10m 단순화 뒤 45° 이상 꺾임 횟수/km'이고 J는 '외접 크기 4% 단순화 대비 길이 초과'다. 서로 다른 것을 재므로 앞의 것을 세게 눌러도 J가 일관되게 줄지 않는 것으로 보인다(사후 해석).
- 이번 기본 그림(하트·별·고양이)의 J는 대체로 작다(중앙값 0.016, v19 사물 그림 0.037). 사용자가 지적한 '삐죽삐죽'은 일부 경로에 몰려 있을 수 있어 중앙값 기준이 둔감했을 수 있다.
- 다음 후보 H4c(미실행): 탐색 목적함수에 J와 같은 척도(크기 비례 단순화 대비 길이 초과)를 직접 넣는다. 새 사전 등록과 다른 개발 지역이 필요하다. 기술 기준을 통과해도 인식 판정(사람 또는 사용자가 허락한 AI 평가자) 전에는 앱 기본값을 바꾸지 않는다.

## 바꾼 코드
- `TUNING.searchZigzag`(기본 0.03): 네 탐색 목적함수의 지그재그 계수를 한곳에 모았다. 기본값이라 앱 결과는 그대로다. 표시 유사도 공식은 건드리지 않았다.
- `orderedContourPath`의 `turnCost`(기본 0.03), `QualityOptions.contourTurnCost`: 실험용, 앱은 넘기지 않는다.
